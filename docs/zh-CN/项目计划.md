# agent-sentinel 项目计划

> 本文档面向课程验收，记录项目定位、目标、范围、技术选型、里程碑与分工建议。
> 仓库的其余文档（`README.md`、`docs/*.md`）使用英文，便于开源协作。

## 一、项目定位

**一句话：为编码智能体（coding agent）提供"护栏 + 黑匣子"。**

编码智能体是一类会直接修改文件、执行命令、访问网络的程序。使用者面对两个
现实问题：

1. **边界问题**：如何限制它"能做什么"。一次 `rm -rf`、一次 `git push --force`、
   一次把密钥写进日志，代价都不可逆。
2. **追溯问题**：它"到底做了什么"。三天后需要回答"是谁改了这个文件、当时谁
   批准的"，必须拿得出证据。

agent-sentinel 用两个核心模块分别回答这两个问题：

| 支柱 | 回答的问题 | 代码位置 |
| --- | --- | --- |
| 护栏（Guardrails） | 这个动作能不能执行？ | `src/agent_sentinel/policy/` |
| 飞行记录仪（Flight recorder） | 提了什么、判了什么、发生了什么？ | `src/agent_sentinel/journal.py` |

## 二、要解决的问题（与现有做法的差距）

| 常见做法 | 问题 |
| --- | --- |
| 只靠提示词约束模型 | 不可验证、不可审计，越狱即失效 |
| 只靠容器/虚拟机隔离 | 解决"能不能破坏系统"，但不记录"智能体想做什么" |
| 只打日志 | 日志可被改写，事后无法证明完整性 |
| 人工盯着看 | 不可持续，且没有留下结构化记录 |

agent-sentinel 的差异化在于：**策略是可评审的数据（TOML 文件），日志是不可
事后篡改的哈希链**，两者都由一个不引入任何第三方运行时依赖的库实现。

## 三、范围

### 本项目做

- 用声明式策略对动作给出 `allow` / `review` / `deny` 三态判定，并说明理由；
- 把"提出动作 → 策略判定 → 执行结果"完整写入追加型日志；
- 通过逐条哈希链让日志的篡改、删除、乱序可被检测；
- 提供命令行工具 `sentinel` 与 Python 库两种接入方式；
- 内置 `permissive` / `standard` / `strict` 三套策略预设。

### 本项目不做（明确写清以免过度承诺）

- 不做沙箱、容器或内核级隔离；
- 不阻止日志被篡改，只**检测**篡改；
- 不做依赖漏洞扫描、密钥静态扫描；
- 不解析命令语义，正则匹配是文本级过滤。

详细威胁模型见 [`../threat-model.md`](../threat-model.md)。

## 四、技术选型

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 语言 | Python 3.11+ | 智能体运行环境普遍具备；`tomllib` 自 3.11 起进入标准库 |
| 运行时依赖 | **零依赖** | 安全工具引入的依赖本身就是新的攻击面 |
| 策略格式 | TOML | 标准库可直接解析，原生支持多行字符串（正则友好），支持注释 |
| 日志格式 | JSON Lines + SHA-256 哈希链 | 纯文本、可 grep、可 diff、可脱离本库校验 |
| 仓库布局 | `src/` 布局 + Hatchling | 避免测试误导入工作目录；打包产物可靠 |
| 质量工具 | pytest / ruff / mypy / pre-commit / GitHub Actions | 见 `docs/development.md` |

架构决策的完整记录见 [`../adr/`](../adr/)。

## 六、当前进度与验证方式

已完成部分均可复现验证：

```console
$ python -m pytest                      # 125 passed
$ python -m pytest --cov=agent_sentinel # 覆盖率约 94%
$ python examples/quickstart.py         # 端到端演示
$ sentinel policy check --policy standard --target "rm -rf /"

```

## 七、分工建议（3–4 人）

| 角色 | 负责内容 | 对应文件 |
| --- | --- | --- |
| 策略引擎 | 规则模型、优先级、加载校验、预设维护 | `policy/` |
| 记录与完整性 | 事件格式、哈希链、校验报告、导出 | `events.py`、`journal.py` |
| 执行守卫 | 受控执行、审批回调、超时、文件/网络守卫 | `guards/`、`cli.py` |
| 测试与文档 | 用例设计、CI、文档、演示脚本 | `tests/`、`docs/`、`examples/` |

建议以「策略规则」和「事件格式」为两条稳定的接口边界，人员可并行开发。

## 八、验收要点（可量化）

1. 能对一段命令给出三态判定，并说明命中的规则与理由；
2. 一次受控执行产生完整的三条记录（提出/判定/结果），且可通过 `journal verify` 校验；
3. 人为改动日志任意一行后，`journal verify` 必须报错并指出行号与原因；
4. 内置策略能正确拒绝 `rm -rf /`、拦截 `..` 路径逃逸、将 `git push --force` 置为待审核；
5. 待审核的动作必须经 `sentinel approve` 记录批准后才能执行，且该批准只能使用一次；
6. 全量测试通过，CI 绿灯，覆盖率不低于 85%。
